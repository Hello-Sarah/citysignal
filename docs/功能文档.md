# 功能文档 · CitySignal

## 1. 问题定义

异地情侣里，人在湾区的一方常常"不知道这周有什么可以去"。
市面上的活动聚合站（Funcheap、Eventbrite、各种 allevents 站点）有两个问题：

1. **信息密度低而噪音高** —— 一周几百条，绝大部分不相关。
2. **准确性没有分级** —— 聚合站把"官网确认的音乐节"和"某个转发了三手的社群小聚"排在一起，
   读者无法判断哪条值得专程跑一趟。第二类信息在华人社群活动里尤其普遍：
   很多活动只在小红书/微信群里流传，没有任何官方页面。

**这个项目要解决的不是"聚合更多活动"，而是"每周给一个具体的人，一份可信度已经标好的短清单"。**

## 2. 用户与场景

| 角色 | 是谁 | 场景 |
|------|------|------|
| 编辑者 | 项目作者，在香港 | 每周花 10–20 分钟，把搜到的 + 收到的小红书链接整理成一期 |
| 读者 | 男友，在旧金山做 MLE | 周三早上收到邮件，扫一眼精选，点进网页看完整清单，周末决定去哪 |

关键约束：**读者不装 App、不注册、不登录**。所以产出必须是"一封邮件 + 一个点开就能看的公开网页"。

## 3. 功能清单

### 3.1 三级可信度标注（核心功能）

每条活动带一个 `Status`，页面上用不同颜色的徽章区分：

| 标注 | 判定标准 | 视觉 |
|------|---------|------|
| **已核实** | 官方/政府信源确认：`.gov`、场馆官网、主办方官网或主办方自有票务页 | 绿底白字 |
| **场地已核实** | 地址确认属实，但活动细节只有聚合站等二手来源 | 绿字绿边框 |
| **未核实** | 查不到任何独立信源（多为小红书上的社群小活动） | 红字红边框 |

**设计决策：`未核实` 的条目不删除，照常展示。**

这是本项目最重要的产品决策。常见做法是"查不到就不收录"，但那会系统性地过滤掉华人社群自办的小活动——
恰恰是读者最难从主流渠道获得、也最想知道的那部分。项目的选择是：**保留内容，但绝不冒充可信度**。
读者自己决定要不要为一条"未核实"的活动跑一趟。

配套的硬规则（写进了每周自动化任务的提示词里）：
- 绝不因为"查不到"就编造信息或删除内容
- 遇到信源冲突（聚合站说办一天、官网说办两天）→ **以官方为准，并把冲突如实告知编辑者**，
  不允许自己挑一个"看起来对的"就悄悄定论

### 3.2 精选标记（Pick）

`Pick` 列非空的条目会被高亮（金色描边 + "给你挑的"徽章），并在周三邮件里优先列出。

判断依据是读者本人的偏好画像（本项目里是：新店/市集/吃、展览/艺术、流行文化与极客向内容）。
这是**人工策展**，不是算法推荐——数据量只有每周 20 条上下，人的判断比任何排序模型都准，
而且偏好可以随时口头调整、当场生效。

### 3.3 周报网页

- 公开链接，无需登录（`执行身份 = 作者`，`访问权限 = 任何人`）
- 三个分区：三藩市市内 / 湾区市外 / 华人社群活动
- 车票（ticket stub）视觉隐喻：左联放类别标签和日期，右联放标题、地址、价格、核实徽章、地图链接
- 侧边栏列出所有历史期次，点击切换（`?week=YYYY-MM-DD`）
- 移动端响应式（读者主要在手机上看）

### 3.4 周三定时邮件

每周三上午 9 点自动发出，内容是当期前 5 条（精选优先），附完整周报链接。
发信走作者自己的 Google 账号，**不接入任何第三方邮件服务**——这是隐私上的刻意选择。

### 3.5 发信前预览（previewWeeklyEmail）

`previewWeeklyEmail()` 用和正式发信**完全相同的代码路径**生成邮件，
但只发到 `CONFIG.PREVIEW_ALSO`（编辑者自己的邮箱），不碰 `RECIPIENT_EMAILS`。

加这个函数的直接原因是缺陷 6 和 7：**邮件的排版和链接，只有真正收到一封才能验证**，
而在此之前唯一的验证方式是发给读者本人再问他好不好看——把读者当测试环境。

实现上刻意**不用** `Session.getActiveUser().getEmail()` 自动取所有者邮箱：
那需要额外的 OAuth 范围（读取账号邮箱），为一个预览功能扩大脚本权限不划算，
把地址写进配置就够了。**权限该省则省**。

### 3.6 每周编辑流水线

一个每周一触发的自动化任务，负责：
1. 主动搜索本周 SF + 湾区活动，按验证方法论逐条核实
2. 提醒编辑者补充小红书/社群渠道的活动（这部分无法自动化，见 §6）
3. 把新一期数据追加写入 Google Sheet
4. 打开网页确认新一期渲染正常
5. 确认周三邮件的定时触发器仍然存在

## 4. 测试与评估

### 4.1 数据层：自动化校验

`tests/validate_data.py` 是可运行的数据校验器，覆盖 8 类规则：

| # | 规则 | 级别 | 由来 |
|---|------|------|------|
| 1 | 表头与列数完全匹配 | ERROR | 列错位会让整期数据渲染错乱 |
| 2 | 必填字段非空（WeekId/Zone/Category/Title/Location/Status） | ERROR | — |
| 3 | 单元格不以 `=` `+` `@` 开头 | ERROR | 防 Sheets 公式注入 |
| 4 | `WeekId` 是合法日期且为周三 | ERROR / WARN | 周三对齐发信日；早期曾误用周一 |
| 5 | `Zone`、`Status` 取值在枚举内 | ERROR | 非法 Zone 会导致整块内容不渲染 |
| 6 | `SubGroup ≠ Title`；华人社群区的 SubGroup 必须是地区 | ERROR | **真实缺陷**：曾导致每个活动上方重复打印自己的标题 |
| 7 | `MapLink` 为空或 `https://` 开头 | ERROR | **真实缺陷**：曾有微信号被填进 MapLink，页面上渲染出跳 404 的按钮 |
| 8 | 同一期内标题不重复 | WARN | 防重复录入 |

**回归用例**：`tests/fixtures_bad.tsv` 里固化了 7 条已知缺陷（含上述两个真实线上 bug），
每次改校验器都要确认它们仍被抓出。当前基线：**8 个 ERROR + 7 个 WARN，退出码 1**。

```bash
python3 tests/validate_data.py data/sample_events.tsv      # 期望：通过，退出码 0
python3 tests/validate_data.py tests/fixtures_bad.tsv      # 期望：8 ERROR，退出码 1
```

### 4.2 内容层：核实率作为质量指标

校验器同时输出每期的**核实率**（`已核实 / 总条目`）和核实等级分布。这是这个项目里
最接近"准确率"的可度量指标，也是判断某一期够不够扎实的依据。

历史数据：

| 期次 | 条目 | 已核实 | 场地已核实 | 未核实 | 核实率 | 备注 |
|------|------|--------|-----------|--------|--------|------|
| 2026-08-26 | 33 | 17 | 12 | 4 | 52% | 含 16 条社群渠道来源的活动 |
| 2026-09-02 | 31 | 23 | 6 | 2 | 74% | 20 条主动搜索 + 11 条社群渠道补充 |

核实率的高低本身不是好坏——**社群活动占比越高，核实率必然越低**，这是内容构成决定的，
不是质量下降。真正要看的是：`未核实` 的条目有没有被如实标注，以及信源冲突有没有被记录。

第二期是个现成例子：只有主动搜索的内容时核实率 75%，补进 11 条社群渠道内容后落到 74%。
落的那一点正是两条只在社群渠道流传、官方渠道完全查不到的活动——
它们**没有被删掉**，而是照常展示并标红。这正是这个指标该有的行为。

### 4.2.1 信源冲突的处理（第二期实例）

同一批数据里出现过两类冲突，处理方式不同：

| 冲突 | 处理 |
|------|------|
| 社群渠道写票价 $35+，主办方官方报名页是 $49.99 起 | **以官方为准**，同时把社群渠道的说法写进 `PriceInfo` 括注，让读者知道差异存在 |
| 社群渠道说活动今晚举行，主办方报名页已标记 Past Event | **无法判定**孰真——可能只是报名截止。不擅自选一个，状态压到 `场地已核实`，`Note` 写明「出发前请再确认」 |

区别在于：第一类是**可判定的冲突**（官方优先级更高），第二类是**不可判定的冲突**
（两个信源说的可能是不同的事）。可判定的按规则定；不可判定的如实交给读者。

### 4.3 渲染层：部署后人工验证

Apps Script 的 Web App 有一个容易踩的坑：**改代码 + 保存 ≠ 线上生效**。
定时触发器跑的是 HEAD 代码（保存即生效），但网页跑的是版本化部署，必须显式发布新版本。
因此每次改动网页相关代码后，验证清单是：

1. 打开 `/exec` 链接，**等满 10 秒**（Apps Script 首屏加载慢，白屏不等于挂了）
2. 确认默认显示最新一期，侧边栏历史期次齐全
3. 确认三个分区标题、小节标题、核实徽章颜色、地图链接、精选高亮都正常
4. 滚动到底，确认最后一条完整渲染（曾出现过侧边栏 `position:sticky` 在 iframe 内失效、
   撑出大片空白的问题）
5. 出问题时看 Apps Script 的「执行记录」面板：`已完成` 说明 `doGet` 没抛异常，
   问题在渲染层；`失败` 则点进去看堆栈

### 4.4 已修复缺陷登记

| # | 现象 | 根因 | 修复 |
|---|------|------|------|
| 1 | 网页整个打不开，报 `weekId.split is not a function` | Sheets 把 `2026-08-26` 自动识别成日期类型，`getValues()` 返回 `Date` 而非字符串 | 新增 `cellToString_()`，`Date` 统一用 `Utilities.formatDate` 转回字符串；所有单元格读取都走它 |
| 2 | 滚动时页面上方出现大片空白 | 侧边栏 `position:sticky; height:100vh`，但 Apps Script 把用户 HTML 装进 iframe，滚动容器是外层页面，sticky 失效 | 侧边栏改普通流式布局；给 `html` 补底色防露白边 |
| 3 | 每个社群活动上方重复打印自己的标题 | `SubGroup` 被填成了活动名，而它会被渲染成小节标题 | 改为按地区分组；校验器加规则 6 防复发 |
| 4 | 地图按钮点了跳 404 | 微信号被填进 `MapLink` 列 | 渲染前校验 `^https?://`；校验器加规则 7 防复发 |
| 5 | 标题含 `&` `<` 时页面结构损坏 | 模板字符串直接插值，未转义 | 新增 `esc_()`，所有用户内容转义后再插入 HTML |
| 6 | 邮件主题和正文出现 `������` | 主题里放了一个票券 emoji。源码里它是完好的（合法 UTF-8，编辑器显示正常），是 **非 BMP 的 4 字节字符没扛过邮件头编码**。中文是 BMP 内的 3 字节字符，从没出过问题 | 主题与正文一律不放 emoji，并在代码里注释原因防复发 |
| 7 | 邮件里「查看完整周报」按钮点开是 Google 权限错误页 | 链接用 `ScriptApp.getService().getUrl()` 动态取。**从编辑器手动运行时它返回 `/dev` 开发版地址**，那个地址只有对脚本有编辑权限的人能打开 | `CONFIG.SITE_URL` 写死 `/exec` 公开地址，发信只用它（网页侧边栏仍用动态取——Web App 上下文里返回的本来就对） |
| 8 | 以为邮件发出去了，其实跑的是别的函数 | Apps Script 编辑器的函数下拉框**会运行「上一次」的选择**：点完下拉项立刻点运行，选择还没提交 | 选完刷新页面再运行；跑完去「脚本执行」页核对函数名——「执行日志」只显示 `Logger.log` 输出和起止通知，**不显示实际运行的函数** |

### 4.5 尚未覆盖的部分（诚实说明）

- **没有端到端自动化测试**。Apps Script 没有本地运行时，网页和邮件的验证目前靠人工清单。
  可行的改进方向是把 `doGet` 的渲染逻辑抽成纯函数，在 Node 里对固定输入做快照测试。
- **邮件送达没有监控**。定时触发器失败只会写进 Apps Script 的执行日志，
  读者那边表现为"邮件不来了"，可能几周后才被发现。改进方向是让每周任务顺带检查上次执行状态。
- **"执行完毕"不等于"发出去了"，更不等于"送达了"**。缺陷 8 就是这么misread的：
  日志显示成功，但跑的根本是另一个函数。而即使函数跑对了，`GmailApp.sendEmail`
  只保证 Gmail 接收了发送请求——地址写错的话退信是异步回到发件人邮箱的，脚本这边照样"成功"。
  唯一可靠的验证是**看收件人实际收到的原件**。缺陷 6 和 7 都是这样才发现的。
- **核实状态会过期**。标记为"已核实"是标注当时的结论，活动可能取消或改期，目前没有复查机制。
- **校验器拦不住"事实过期"**。第二期处理社群渠道链接时，其中一条是**去年同月**发的，
  正文只写「9月5日」不写年份，11 条活动全是过期内容。这类数据在 schema 上完全合法，
  校验器一条都抓不出来——它校验的是**结构**，不是**事实**。
  目前的缓解手段是流程性的（编辑流水线要求「先滚到底确认发帖日期」），不是自动化的。
- **渲染层的人工验收在浏览器自动化下做不到**。Apps Script 把页面装进沙盒 iframe，
  自动化滚不动它、也读不到里面的文本，所以 §4.3 的逐条肉眼清单只能由人来做。
  自动化能给的替代证据有两条：页面整体渲染成功（`doGet` 全量读表，任何一行坏掉都会 500），
  以及校验器对新增数据的独立检查。

## 6. 已知限制

**小红书内容无法自动化采集。** 站点有反爬机制，`robots.txt` 会拦截抓取工具，
浏览器自动化不稳定，也没有合规的公开 API。因此社群活动这一块**必须靠人主动转发链接**。

项目对此的处理不是硬绕过，而是**把自动化的边界划在这里**：
人负责"发现"（转发链接），自动化负责"验证 + 结构化 + 录入 + 发布"。
这条边界是刻意的——试图绕过站点的反爬措施既不可靠也不合适。
