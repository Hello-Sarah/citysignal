# 技术文档 · CitySignal

## 1. 架构

```
┌─────────────────┐
│  编辑者（每周）   │  搜索 + 核实 + 补充社群渠道内容
└────────┬────────┘
         │ 追加写入
         ▼
┌─────────────────────────────┐
│  Google Sheet · Events 标签页 │  单一数据源（12 列 × N 行）
└────────┬────────────────────┘
         │ SpreadsheetApp.openById().getDataRange().getValues()
         ▼
┌─────────────────────────────────────────────────┐
│  Google Apps Script  (src/Code.gs)              │
│                                                 │
│   doGet(e) ──────────► 服务端渲染 HTML 字符串     │
│                        HtmlService 输出          │
│                                                 │
│   sendWeeklyEmail() ─► GmailApp.sendEmail()      │
│        ▲                                        │
│        │ 每周三 09:00                             │
│   ClockTriggerBuilder（由 createWeeklyTrigger 建）│
└──────┬──────────────────────────┬───────────────┘
       │ Web App 部署（版本化）      │ 触发器（跑 HEAD）
       ▼                          ▼
  公开网页 /exec              读者收件箱
```

**为什么是 Apps Script 而不是常规 Web 栈**

| 候选方案 | 否决原因 |
|---------|---------|
| Netlify / Vercel + 静态站 | 不支持持久化数据更新——每周更新内容要重新部署，且没有现成的定时发信能力 |
| 独立后端 + 数据库 | 对每周 20 条数据的场景严重过度设计；还要额外承担服务器与域名成本 |
| 第三方邮件服务（SendGrid 等） | 需要把收件人邮箱交给第三方；作者明确出于隐私考虑拒绝 |
| **Apps Script** ✅ | 零成本、零运维；Sheet 天然是编辑者能直接用的 CMS；发信走作者自己的 Google 账号，收件人地址不出 Google 生态；定时触发器内置 |

代价是被 Google 生态锁定，以及本地开发体验差（无本地运行时、无包管理）。
对这个规模的项目，这笔交易是划算的。

## 2. 代码结构（`src/Code.gs`，约 400 行，单文件）

```
CONFIG                    SHEET_ID / CITIES / RECIPIENTS / SITE_URL / PREVIEW_ALSO
├─ citiesList_()          城市配置列表
├─ findCityBySlug_()      ?city=hk -> 城市对象；非法值返回 null
├─ findCityByLabel_()     Sheet 里的 City 列值 -> 城市对象
├─ defaultCity_()         配置里的第一个城市
│
├─ doGet(e)               Web App 入口，处理 ?city= 与 ?week=，都非法则回落默认
├─ readAllEvents_()       读 Sheet → 数组of对象，所有单元格过 cellToString_()
│   └─ cellToString_(v)   类型归一化：Date → 'yyyy-MM-dd'，其余 → trim 后的字符串
├─ getSortedWeekIds_(data, city)  该城市的期次，去重 + 倒序
├─ renderPage_(data, city, ...)  组装完整 HTML（城市 tab + 往期侧边栏 + 主体）
│   ├─ formatWeekLabel_() '2026-09-02' → '09.02 那一周'
│   ├─ renderZone_()      按 Zone 过滤 → 按 SubGroup 分小节
│   └─ renderTicket_()    单条活动的车票 DOM
│       └─ esc_(v)        HTML 转义
├─ PAGE_CSS_              页面样式（模板字符串常量）
│
├─ sendWeeklyEmail()      正式发信：遍历城市，按 RECIPIENTS 的订阅各发一封
├─ previewWeeklyEmail()   预览：每个有数据的城市各发一封给 PREVIEW_ALSO，不碰读者
└─ sendIssueTo_(to, city) ← 上面两个都只是它的薄封装；返回 false = 该城市无数据，没发
    └─ renderMailItem_()  邮件里的单条活动（table + 内联样式版车票）
        └─ esc_(v)

└─ createWeeklyTrigger()  幂等地重建"每周三 9:00"触发器（先删同名再建）
```

**为什么把发信拆成 `sendIssueTo_(to)`**：预览和正式发信如果是两套代码，
预览就失去意义了——你验证的不是真正会发出去的那封。现在两者共用同一条渲染路径，
唯一的差别是收件人参数。

### 2.1 服务端渲染，无前端框架

整个页面是在 Apps Script 里拼出来的一个 HTML 字符串，没有客户端 JS。
选择理由：内容是纯静态展示，数据量小（每期 ~20 条），
引入框架只会增加 iframe 内的加载时间——而 Apps Script 的 Web App 首屏本来就慢。

历史期次切换用的是普通链接 `?week=2026-08-26`，走完整的服务端往返，不做 SPA。

### 2.2 关键实现细节

**类型归一化 `cellToString_()`**

```javascript
function cellToString_(v) {
  if (v === null || v === undefined) return '';
  if (Object.prototype.toString.call(v) === '[object Date]') {
    return Utilities.formatDate(v, Session.getScriptTimeZone(), 'yyyy-MM-dd');
  }
  return String(v).trim();
}
```

Google Sheets 会把形如 `2026-09-02` 的输入自动识别成日期类型，
`getDataRange().getValues()` 返回的是 JS `Date` 对象。
早期版本直接对 `WeekId` 调 `.split('-')`，线上表现为整个页面 500。
现在所有单元格读取统一过这个函数，`Date` 用脚本时区格式化回字符串。

**HTML 转义 `esc_()`**

所有来自 Sheet 的内容在插入模板字符串前都过 `esc_()`（`& < > " '` 五个字符）。
`MapLink` 额外做协议白名单校验（`/^https?:\/\//i`），非链接内容不渲染 `<a>`。

**链接必须写死，不能动态取 `SITE_URL`**

```javascript
// 曾经是 ScriptApp.getService().getUrl()
const link = CONFIG.SITE_URL + '?week=' + latestWeek;
```

`ScriptApp.getService().getUrl()` 的返回值**取决于执行上下文**：
在 Web App 里跑（`doGet`）返回的是公开的 `/exec`，但**从编辑器手动运行函数时返回 `/dev`**。
`/dev` 只有对脚本有编辑权限的人能打开，收件人点进去看到的是 Google 的权限错误页。

麻烦的地方在于**脚本这边完全不报错**——邮件正常发出，日志显示成功，
只有真的去点那个按钮才会发现。所以发信路径改成读 `CONFIG.SITE_URL`；
`renderPage_()` 里的侧边栏仍用动态取，那里的执行上下文永远是 Web App，返回的本来就对。

> ⚠️ `SITE_URL` 只在**新建部署**时才会变（发布新版本不会变）。真要新建部署，记得回来改。

**邮件正文里不能出现 emoji**

主题里曾放过一个票券 emoji，收件人那边收到的是一串问号方块。
排查后确认**源码是好的**（合法 UTF-8，编辑器显示正常）——
是这个**非 BMP 的 4 字节字符没扛过邮件头编码**。
中文是 BMP 内的三字节字符，从来没出过问题。现在主题和正文一律不放 emoji，
代码里留了注释说明原因防止复发。

**邮件 HTML 用 table + 内联样式，不用 flex/grid**

`renderMailItem_()` 把网页上的车票存根重新实现了一遍，视觉一致但技术手段完全不同：
外层 `<table>`，撕票线用单元格的 `border-right: 1px dashed`，所有样式内联。
原因是邮件客户端对 flex/grid 支持很差，`<style>` 块也常被剥掉。
**这是刻意的重复实现，不是没抽象好**——网页和邮件的渲染约束不一样，强行共用只会两头都别扭。

**幂等的触发器创建**

```javascript
ScriptApp.getProjectTriggers().forEach(t => {
  if (t.getHandlerFunction() === 'sendWeeklyEmail') ScriptApp.deleteTrigger(t);
});
ScriptApp.newTrigger('sendWeeklyEmail').timeBased()
  .onWeekDay(ScriptApp.WeekDay.WEDNESDAY).atHour(9).create();
```

先清同名触发器再建，所以 `createWeeklyTrigger()` 可以安全地重复运行，不会累积出多个触发器。

### 2.3 多城市：为什么 City 是配置而不是硬编码

`CONFIG.CITIES` 里每一项自带 `slug`（URL 用）、`label`（Sheet 里存的值）、
`siteTitle`、`eyebrow`、`mailName` 和 `zones`。**加一个城市不需要改任何渲染或发信代码。**

几个刻意的决定：

**分区（`zones`）跟着城市走，不是全局枚举。** 湾区是「市内 / 市外 / 华人社群活动」，
香港是「港岛 / 九龙 / 新界」。早期版本 `renderPage_` 里写死了
`const zones = ['三藩市市内', '湾区市外', '华人社群活动']`——那一行是整个多城市改造
最先要拆掉的东西，也是加城市时最容易被忘掉的耦合点。

**期次按城市隔离。** `getSortedWeekIds_(data, city)` 只返回该城市有数据的期次。
如果做成全局期次列表，三藩市出了新一期就会让香港的页面跳到一个空日期上。

**每个城市有自己的 `siteTitle` 和 `mailName`，而不是共用一个全局标题。**
直接原因是加香港时不能改动三藩市读者已经看惯的字：
`mailName` 保持 `湾区`，所以现有读者收到的邮件主题一字未变。
**做加法的改动不应该让已有用户察觉到变化。**

**空数据的城市不发信。** `sendIssueTo_` 在该城市没有任何一期时返回 `false`。
一封「本周没有内容」的邮件是噪音，而且会让「收到邮件 = 有新内容」这个约定失效。

**页面上城市是筛选器，不是生成按钮。** 切换城市走的是普通链接 `?city=hk`，
和期次切换同一套服务端往返机制。页面不产生内容——内容由每周任务先核实后入库。

### 2.4 CSS 设计约束

视觉是"车票存根"隐喻：`.ticket` 是 flex 容器，左边 `.stub` 用 `border-right: 2px dashed` 做撕票线。
配色取自旧金山的雾（`--fog: #c9d2d4`）和纸质车票（`--paper: #f2ecdc`），
字体用 Fraunces（衬线，标题）+ IBM Plex Mono（日期与地址，强调"票据感"）。

**踩过的坑**：侧边栏最初用 `position: sticky; height: 100vh`。
Apps Script 把用户 HTML 装进一个 iframe，而 iframe 的高度被撑到内容全高，
真正的滚动容器是外层页面——sticky 因此失效，`100vh` 还撑出大片空白。
改成普通流式布局解决。**在 Apps Script Web App 里，任何依赖视口的定位都要先验证。**

## 3. 数据层

见 [`data/schema.md`](../data/schema.md)。要点：

- 单一数据源就是一张 Sheet，没有数据库
- 13 列固定 schema，`City` + `WeekId` 做逻辑分区（同城市同 WeekId = 一期）
- 没有主键、没有关联表——数据量不需要
- 每次 `doGet` 全量读表。当前 53 行，耗时可忽略；
  数据涨到几千行时需要改为按 `WeekId` 过滤后再读，或加缓存

## 4. 部署

两条**互不相同**的生效路径，是这个平台最容易搞错的地方：

| 改动内容 | 生效方式 |
|---------|---------|
| `sendWeeklyEmail()` 等触发器调用的逻辑 | **保存即生效**。触发器绑定的是 HEAD 版本 |
| `doGet()` / 渲染 / CSS | **必须发布新版本**：部署 → 管理部署 → 编辑 → 版本选「新版本」→ 部署 |

Web App 部署配置：
- 执行身份：**作者本人**（脚本需要以作者身份读 Sheet 和发信）
- 访问权限：**任何人**（读者不需要 Google 账号即可打开）

> ⚠️ **新建部署会换掉 `/exec` 地址**，此时必须回头改 `CONFIG.SITE_URL`，
> 否则邮件里的链接会指向旧部署。发布新版本（同一个部署改版本号）不受影响。

OAuth 授权范围：
- `spreadsheets`（读数据）
- `gmail.send` / `script.send_mail`（发信）
- `script.scriptapp`（创建触发器）——**这一项不在首次部署的授权范围内**，
  第一次运行 `createWeeklyTrigger()` 会因缺少它而失败，需要按错误提示补授权一次

**刻意没有申请的范围**：`userinfo.email`。
`previewWeeklyEmail()` 最初用 `Session.getActiveUser().getEmail()` 自动取所有者邮箱，
一运行就弹授权框。为一个预览功能扩大脚本的权限不划算，改成把地址写进
`CONFIG.PREVIEW_ALSO` 就够了。**能不要的权限就不要。**

### 4.1 手动运行函数的两个坑

**下拉框显示的函数 ≠ 实际运行的函数。** 点完函数下拉项**立刻**点「运行」，
选择还没提交，跑的是**上一次**选中的那个。曾经因此把 `doGet` 当成 `sendWeeklyEmail`
跑了一遍，然后根据「执行完毕」误判邮件已发出。
正确做法是选完**刷新页面**（重载后显示的才是真正生效的），再运行。

**「执行日志」不显示跑了哪个函数。** 它只有 `Logger.log` 的输出和起止通知。
要确认实际执行的函数，去左侧「**脚本执行**」页看 `函数` 那一列。

**危险相邻**：函数下拉框里 `sendWeeklyEmail` 紧邻 `previewWeeklyEmail`，
选错点运行会直接把邮件发给读者。运行前务必确认下拉框内容。

## 5. 自动化编辑流水线

一个每周一触发的定时任务，携带完整上下文（资源链接、字段规则、验证方法论、边界约束），
在全新会话里执行 §功能文档 3.5 描述的五个步骤。

设计上的两个要点：

1. **提示词是"可执行的运行手册"**，不是概要。它包含具体的 URL、
   字段枚举值、踩坑提醒（例如"函数下拉框里 `sendWeeklyEmail` 就在 `createWeeklyTrigger` 上面一格，
   选错点运行会立刻发一封邮件出去"），因为每次触发都是无记忆的新会话。
2. **人的确认点是硬编码的**：OAuth 授权、Google 账号的「允许」按钮一律不代点；
   编辑者没回复就不编造内容，安静结束。

## 6. 安全与隐私

| 关注点 | 处理 |
|--------|------|
| 收件人邮箱 | 只存在于作者自己的 Apps Script 配置里，不经过任何第三方服务 |
| 网页公开性 | `/exec` 是无鉴权公开链接。内容只有公开活动信息，不含个人数据 |
| 公式注入 | 校验器拦截以 `=` `+` `@` 开头的单元格 |
| XSS | 所有 Sheet 内容经 `esc_()` 转义；`MapLink` 做协议白名单 |
| 仓库脱敏 | `src/Code.gs` 里的 Sheet ID、收件人邮箱、部署地址均已替换为占位符；提交前用脚本硬校验一次，真实值不进版本库 |
| OAuth 最小权限 | 主动放弃 `userinfo.email`（见 §4）。脚本只持有读表、发信、建触发器三项 |
| 发信前预览 | `previewWeeklyEmail()` 走完全相同的渲染路径但只发给编辑者，避免拿读者当测试环境 |

## 7. 本地开发

Apps Script 没有本地运行时，但单文件是合法的 JavaScript，可以做语法检查：

```bash
cp src/Code.gs /tmp/Code.js && node --check /tmp/Code.js
python3 tests/validate_data.py data/sample_events.tsv   # 期望退出码 0
python3 tests/validate_data.py tests/fixtures_bad.tsv   # 回归用例，期望退出码 1
node tests/render_test.js                               # 21 条断言，期望退出码 0
```

`render_test.js` 把 `SpreadsheetApp` / `GmailApp` / `ScriptApp` 等全局对象打桩，
再用 `new Function` 把整个 `src/Code.gs` 求值进一个函数作用域，返回需要的函数。
这样不改动生产代码结构就能在 Node 里跑渲染和发信逻辑——
**Apps Script 没有本地运行时，但它写的终究是合法 JavaScript。**

## 8. 后续改进方向

1. ~~**渲染逻辑纯函数化**~~ —— 已用打桩的方式解决（`tests/render_test.js`），
   不需要重构生产代码。**遗留的真正缺口是浏览器里的视觉验证**：
   快照测试保证 HTML 字符串对，保证不了 CSS 在 Apps Script 的沙盒 iframe 里不塌
2. **城市配置的单一事实来源** —— 校验器的 `CITY_ZONES`（Python）和运行时的
   `CONFIG.CITIES`（Apps Script）各存一份城市→分区映射，靠手工同步。
   两处不一致时校验器会放过运行时渲染不出来的数据。两个城市时人能记住，
   加到四五个就该共用一份 JSON，或让校验器直接解析 `Code.gs`
2. **邮件送达监控** —— 每周任务顺带读取 Apps Script 执行日志，发现触发器失败主动告警。
   注意这只能覆盖「触发器没跑」，覆盖不了「跑了但内容坏了」——
   后者目前靠 `previewWeeklyEmail()` 人工看一眼
3. **核实状态复查** —— 对标注为"已核实"的长期活动定期重新校验，避免信息过期
4. **`clasp` 接入** —— 用 Google 官方 CLI 做本地 ↔ Apps Script 的双向同步，
   让版本库成为唯一事实来源（目前是手工同步）
